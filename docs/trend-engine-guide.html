What every file does, and why the math works the way it does

The source files carry short, professional comments only. Each section names its file at the top so you can hold the code and this page side by side.

FastAPI (app/api/) — reads trend_scores, never computes

The one rule that shapes almost every design decision in this project: the API never scores anything inside a request. Scoring is expensive-ish and only needs to happen once a day, right after new data lands — so it happens in jobs/compute_trends.py, and the API just reads whatever that job most recently wrote. If that job fails, the API keeps serving yesterday's snapshot and says so honestly via /health/ready — degraded, not down.

Data layer

app/config.py, app/database.py

config.py reads environment variables into one typed Settings object (pydantic-settings) — DATABASE_URL, the admin API key, and the ml engine's window/support thresholds. database.py creates the SQLAlchemy engine and session factory, and defines Base, the class every table model inherits from. get_db() is a FastAPI dependency: it opens a session, hands it to whichever route asked, and closes it afterward no matter what happened.

app/models/ — one file per table group

FileWhat it defines
brand.pyBrand — one row per retailer (slug, display name, which scraping tier it uses).
product.pyProduct (static facts: title, category, URL), ProductAttribute (the color/pattern/fabric/etc. table — one row per attribute, never merged onto a synonym list), AttrType (the enum of the 8 possible attribute kinds), and ProductLifecycle — a read-only mapping onto a database view, not a table.
observation.pyObservation — one row per (day, product): price, rank, on-sale flag, in-stock flag. This is the only table that grows every single day.
scrape_run.pyScrapeRun (did brand X's scrape succeed on day Y?) and DroppedRecord (the firewall log — every record the ingest pipeline rejected, and why).
trend.pyTrendSnapshot (one row per computed run) and TrendScore (one row per ranked attribute within that run).

Why is ProductLifecycle a view instead of a table with real columns?

Things like "first seen," "days observed," "lowest price ever," and "is this still listed" are all derivable from observations — they're just a MIN/MAX/COUNT away. If they were stored as columns, every single scrape would have to recompute and rewrite them, and any bug in that rewrite step would leave the table silently wrong. As a view, they're recomputed fresh on every read — they can never drift out of sync with the real data, because they're never "the real data" in the first place, just a live query over it.

app/schemas/ — the API's request/response shapes

Plain Pydantic models with no database logic. common.py has the shared envelope types (Page, ErrorResponse, health responses). brand.py, product.py, and trend.py mirror the corresponding ORM models but only expose what the API actually returns — for example TrendScoreOut renames the database's attr_value nowhere, it's kept the same, but drops internal bookkeeping fields.

app/api/ — HTTP only, no SQL

Each router file under api/v1/ matches one URL prefix (trends.py → /trends, etc.) and does exactly three things per route: parse query params, call one service method, wrap the result in the {"data": ..., "meta": ...} envelope. deps.py holds the two shared dependencies (pagination params, the admin API-key check). router.py just aggregates the five route files under one prefixed router.

app/core/

exceptions.py defines AppError and its subclasses (each with a code and HTTP status); app/main.py's exception handler turns any of them into the standard error envelope automatically, so a route just does raise ProductNotFoundError(...) and never touches HTTP status codes directly. logging.py configures structured JSON logs. cache.py is a ~20-line in-process TTL cache — no Redis, because at this data scale a dictionary with timestamps is enough.

The engine — every calculation, in order

app/ml/features.py — build_panel()

This function turns three flat tables into the shape the scoring math actually needs: a panel, meaning a table where rows are days and columns are attributes. Think of it as turning "here's a list of things that happened" into "here's how popular each attribute was, day by day" — a spreadsheet the rest of the math can just do arithmetic on.

Step 1 — the share table (S)

For every (day, attribute) pair, share is: how many distinct products carried that attribute that day, divided by how many products of that same attribute type were observed that day. So "share of dress" isn't "dresses ÷ everything," it's "dresses ÷ all categories seen that day" — comparing dress against top and trousers, not against the color black.

Worked example — 3 days, category attributes only

dresstoptotal
Day 04610
Day 15510
Day 27310

share(dress, day 2) = 7 / 10 = 0.70 — dress went from 40% of the category mix to 70% over 3 days. That's the raw signal everything downstream reacts to.

MIN_SUPPORT = 8 means an attribute only gets scored if it averaged at least 8 products/day — a color three different stores happened to mention twice doesn't get to claim a trend.

Step 2 — restock and disappearance, masked by brand-day validity

This is the densest code in the whole project, so here it is one array at a time. Four boolean matrices, each shaped (products × days):

NameMeaning
presWas this product observed on this day? (raw presence, ignoring scraper failures)
bdDid this product's brand get successfully scraped on this day at all?
BAbd, broadcast onto each product's own row (via p2b, the product→brand lookup)
Mpres & BA — "genuinely present," meaning both actually observed and the day wasn't a scraper failure
Disappearance, for the transition from day t to day t+1
dis_mask = M[t] AND (NOT M[t+1]) AND BA[t] AND BA[t+1]

In words: a product counts as having disappeared only if it was really there on day t, really gone on day t+1, and both of those days had a working scrape for its brand. Restock is the exact mirror — absent on day t, present on day t+1, both days valid.

Worked example — why the brand-day mask matters

DayBrand scrapeProduct X seen?
0OKyes
1FAILEDno rows at all
2OKyes

Without the mask: product X looks "present, absent, present" — a disappearance and a restock in two days, pure noise from a scraper outage. With the mask: BA[day 1] = False, so the day-0→1 transition is excluded entirely. Only real presence changes get counted.

If FULL_PRICE_ONLY is on (it is, by default) and sale data exists, a disappearance while the item was on sale doesn't count either — a markdown clearance is the retailer dumping stock, not a genuine sell-through signal.

Step 3 — rolling events onto attributes (by_key)

The restock/disappear matrices above are indexed by product. But scoring happens per attribute ("black," "dress"), and one product can carry several attributes at once. So this step re-sums: for every attribute a product has, add that product's restock/disappear events onto that attribute's running total. A black dress that restocks adds one restock event to both "black" and "dress."

Step 4 — per-brand share (pb)

The same share calculation as Step 1, but broken out by brand instead of pooled — this is what app/ml/engine.py's breadth calculation reads from, to check whether a trend is one store's bet or a genuine market move.

app/ml/engine.py — TrendEngine.rank()

This is where the panel from features.py becomes an actual ranked list. Two independent signals get computed for every attribute, then blended.

Signal 1 — MRTF (restock/disappear, statistically shaped)

Raw restock and disappear rates aren't comparable across attribute types on their own scale, so each gets z-scored within its own type first — meaning: how many standard deviations above or below the average color is this color's restock rate, compared only to other colors, never to categories or patterns (which have completely different base rates).

MRTF score
mrtf = 0.60 × z(restock_rate) − 0.40 × z(disappear_rate)

Restock is weighted positive and higher than disappear's negative weight — restocking is a deliberate reorder decision by a retailer betting real money on demand; a disappearance is a noisier signal (sold out, discontinued, or just delisted for unrelated reasons), so it counts, but less.

Signal 2 — the temporal model (TrendNet, see next section)

Predicts a forward-looking score straight from the recent share sequence. Also z-scored within type before blending, for the same reason as above.

The blend

Final score
score = 0.70 × z(temporal) + 0.30 × mrtf

If TrendNet's weights fail to load for any reason, the engine falls back to MRTF alone and labels the result "model": "mrtf" instead of "trendnet+mrtf" — never silently claims the hybrid when only half of it ran.

Lifecycle stage — v and accel

Splits the scoring window in half and compares the two halves' average share (v — is it trending up or down at all), then splits into thirds and checks whether the most recent third is accelerating away from the middle third even faster (accel).

Worked example

Share sequence over 6 days: [10, 11, 12, 15, 19, 24]

half: first 3 avg = 11.0, last 3 avg = 19.3 → v = +8.3 (rising)
thirds: [10,11], [12,15], [19,24] → first=10.5, mid=13.5, last=21.5
accel = 21.5 − 2×13.5 + 10.5 = +5.0 → positive, so this is accelerating, not just rising → classified "emerging." If v is positive but accel isn't, it's "peaking" instead — still up, but the growth rate itself has stopped increasing.

Breadth and confidence

breadth compares each carrying brand's early-window share against its late-window share, and reports the fraction of brands where it went up. It is deliberately reported, not blended into the score — an ablation test showed folding it into the formula hurt accuracy. Instead it gates confidence: an attribute needs at least 5 brands carrying it to be called "high confidence," 3 for "medium," otherwise "low" — a single retailer's merchandising bet isn't a market trend, and the output says so honestly rather than dressing it up.

Mann-Kendall (mk_z, mk_p)

A classical statistical test for a monotonic trend in a sequence — it asks "is this series more often going up than down, across every pair of points, more than chance would predict." It's computed and reported on every result, but like breadth, it is not folded into the score — the same ablation showed it doesn't help once TrendNet and MRTF are already blended. It's in the output as a second opinion a reader can sanity-check against.

Why 0.60 / −0.40 / 0.70 specifically — did you tune these?

No — and that's the honest answer. They're set once from measured ICs during the model's own original testing, not fit to this project's serving data. The temporal weight (0.70) was reported as "flat across 0.2–0.6," meaning the exact value barely matters within that range — it isn't a knob that was cranked until a number looked good.

app/ml/trendnet.py — the TrendNet model

A small neural network, not a big one — 17,681 parameters, versus the 205-million-parameter Chronos-2 foundation model it was benchmarked against. It reads a short sequence of recent share values for one attribute and predicts where that share is headed.

What each piece does

LayerPlain-English job
nn.Embedding(8, 8)Turns "this series is a color" (vs. category/pattern/style) into an 8-number fingerprint the rest of the network can use as context — colors and categories genuinely behave differently, so the model needs to know which kind of series it's looking at.
nn.GRU(1, 64)Reads the share sequence one day at a time and keeps a running 64-number "memory" of the shape of the trend so far — this is the part actually doing the time-series reasoning.
logscaleThe log of the series' average absolute size. Two reasons this is fed in separately: the share sequence itself gets normalized to "ratio of its own mean" before entering the GRU (so the network only sees shape, not scale), and a real 40%-share trend behaves differently than a real 0.5%-share one — logscale is how the model gets that magnitude back.
fuse (3 Linear layers)Concatenates the GRU's memory (64) + the type fingerprint (8) + logscale (1) = 73 numbers, and squeezes them down through 48 → 24 → 1 to a single predicted score.

What is the model actually predicting, in one sentence?

Given the last 4 weeks of an attribute's normalized share pattern, predict how much its share will move over the next few weeks, relative to its own recent average — not an absolute number, a shape-relative one, which is why the same trained weights transfer from H&M's transaction data onto Sri Lankan scrape data at all.

Known limitation — go in with this already on the table

The type embedding only has real training for 4 categories: category, color, pattern, style (tmap in the checkpoint). app/ml/engine.py's scoring loop can hand the model other attribute types too (fabric, sleeve_length, ...) — anything not in tmap silently falls back to type-id 0, sharing category's fingerprint. This is real, it's in the code as shipped, and it's flagged rather than hidden — the honest framing is "the model was validated on 4 attribute types; the others get a usable but unvalidated fallback."

app/ml/category_map.py

The one place raw text does get normalized. A hand-written synonym table ("tee" → "T-shirt", "trousers"/"pants"/"jeans" → "Trousers") is tried first; anything that doesn't match falls through to fuzzy string matching (Python's built-in difflib, cutoff 0.7) against a fixed 25-category list borrowed from H&M's own taxonomy. Unlike color or fabric, retailers describe garment types fairly consistently across sites — "dress" essentially always means dress — so canonicalizing here doesn't throw away the kind of signal that hurt color/fabric accuracy.

Pipeline

jobs/ingest.py

Reads every *_garments.json file the scraper wrote for one day, and for each garment: filters out inappropriate items (a keyword list — lingerie, swimwear, etc.), extracts color from whatever structured or free-text signal is available (store-declared variant color first, then shopify tags, then a scan of the title, then the image filename — in that priority order, since each is progressively less reliable), extracts fabric via percentage-aware parsing of composition strings ("70% Cotton, 27% Nylon" picks Cotton, not whichever word is longer), and extracts sleeve/neckline/ silhouette tags from any free-text style description. Everything except category is stored exactly as extracted. Then it upserts the product, inserts today's observation, and records whether the whole brand's scrape succeeded.

jobs/compute_trends.py

The entire job is: build the panel from the database, call TrendEngine.rank() once per horizon (3-day and 5-day), write one trend_snapshots row and its trend_scores rows. Nothing else. This is deliberately the only place scoring happens.

Validation methodology

Run against real Sri Lankan scrape data (23 days × 56 attributes at the time it was run) — three separate tests, deliberately independent of each other.

Test 1 — rolling-origin backtest

Score every attribute using only data available up to day t, then check what actually happened over the following 3 or 5 days — repeated at every possible cutoff day, compared against four baselines (random, current share, recent growth, restock-only).

Test 2 — why a bootstrap CI, not a t-test

The backtest's cutoff days overlap heavily (day 10's 3-day window shares 2 of its 3 days with day 11's window), so they are not independent samples — a standard t-statistic across cutoffs would overstate significance. The fix: compute the effective independent sample size from the series' own autocorrelation (it came out under 1.3 — genuinely that thin), then bootstrap the confidence interval by resampling attributes instead, which really are independent of each other.

Test 3 — ranking stability

Day-to-day Spearman correlation between consecutive days' full rankings: +0.533, with 49% overlap in the top-10 from one day to the next. The intended reading: 0.4–0.8 is the healthy range — high enough that the signal isn't just noise reshuffling itself overnight, low enough that it's actually responsive to new data rather than frozen.

Other questions worth having an answer ready for

You don't have real sales data — what are restock/disappear actually a proxy for?

Whether a retailer put real money behind a reorder. We can't see sales directly from a public storefront, but we can see when a product comes back in stock after being out — that's the retailer's own signal that they believed in continued demand enough to restock it.

How do you know this isn't just overfit to the test window?

Three separate guards: the temporal train/validation split in training is strictly chronological, never random; the non-overlapping-cutoff IC (+0.345) stays close to the overlapping one (+0.428) instead of collapsing, which is what overfitting to a lucky window would look like; and the window-size ablation shows performance degrading smoothly as more (older) context is added — the opposite of what you'd see from a model that memorized the specific test period.

Why not canonicalize color the same way you canonicalize category?

Tested directly, not assumed: merging synonyms measurably lowered accuracy (color IC +0.384 → +0.313 in the source testing). A retailer's specific word choice — "navy" vs. "dark blue" — carries real positioning signal that a synonym merge throws away. Category doesn't have this problem because "dress" means dress everywhere.

What happens if a store's scraper breaks for a day?

jobs/ingest.py still records a scrape_runs row (status failed, with the error message) even when a brand's file is missing or unparseable. app/ml/features.py's brand-day masking then excludes that exact day for that exact brand from restock/disappear counting — so a scraper outage produces zero phantom disappearance events instead of thousands.
